# Translating the app

A proposal. **Nothing here is built yet**, on either side.

Written because the question "can a user pick their language?" has a short
answer — yes — and a long one, which is that the picker is the smallest part of
the job and roughly half of it is not the app's text at all.

---

## 1. What the markets actually ask for

The PRD names **NG, UAE, UK, US and China**. That implies three languages, and
they are not equal amounts of work.

| Language | For | Difficulty |
| --- | --- | --- |
| **English** | NG, UK, US | Done. It is what the app is written in. |
| **Simplified Chinese** | China | Translation, plus a font problem — see below. |
| **Arabic** | UAE | **The whole layout mirrors.** Not a translation job. |

Nigeria is English-speaking for business, so it needs no new language despite
being the largest market on the list.

### Arabic is a different kind of change

Arabic reads right to left, so the interface has to mirror: rows reverse, the
back arrow points the other way, the tab bar flips, progress fills from the
right. React Native supports it, but three things make it awkward:

- On a phone, switching to or from a right-to-left language **requires
  restarting the app**. That is a platform constraint, not a bug to fix.
- Anything positioned absolutely — and this app has several, including the
  score ring and the notification badge — has to be checked by hand.
- It cannot be reviewed on a screenshot. It needs someone who reads Arabic,
  holding a phone.

My recommendation is to leave Arabic out of the first pass entirely and treat
it as its own piece of work.

### The font will break Chinese before the translation does

The app uses Geist and Geist Mono, which are Latin typefaces. They carry no
Chinese characters, so Chinese text will silently fall back to whatever the
device offers and look visibly out of place beside everything else. Needs a
CJK-capable font bundled or a deliberate fallback, before anyone judges the
translation.

---

## 2. The size of the app-side job

- **38 screens and components** carry text.
- Roughly **181 pieces of user-facing wording** — labels, placeholders, hints,
  headings, button text, empty states.
- **There is no translation layer at all today.** Every one of those strings is
  written directly into the screen that shows it.

That is not a large number, and it is the *cheap* part. It also grows: every
screen written between now and whenever this happens adds more.

---

## 3. The part that is not the app's text

This is the finding worth reading. A language picker changes the buttons. It
does **not** change any of this:

| Text the user reads | Where it is written | Language today |
| --- | --- | --- |
| The audit verdict, reasons and action plan | Generated by the AI, backend | English |
| Task descriptions and why evidence failed | Same | English |
| AI mentor answers | Same | English |
| Founder-facing report copy | Same | English |
| Verification and password-reset emails | `notifications/templates.py` | English |

That is the substance of the product. A Chinese-speaking founder with a Chinese
interface would still receive an English audit, English tasks and English
emails — which is arguably worse than an English app, because it looks finished
and is not.

**So the language has to reach the backend.** Concretely:

1. Store the chosen language on the user record. There is **no language or
   locale field on the user today** — I checked.
2. Pass it into the prompts, so the report and the mentor answer in it. The
   rubric prompts have **no language handling** at present.
3. Use it to select the email template. `templates.py` has one language.

Point 2 carries a caveat worth stating to whoever owns the audit: asking a
model to produce its reasoning in another language is not free. Quality varies
by language, and the rubric's criteria are written in English and cite English
evidence. That needs testing per language, not assuming.

### One thing already designed correctly

API errors do **not** need translating server-side. The error envelope carries
a stable `code`, and `CLAUDE.md` says never to parse `message`. So the app can
map each code to its own translated wording, and the server can keep answering
in English. That decision, made for other reasons, happens to make this easy.

---

## 4. Where the setting should live

**Default to the device language, let the user change it, and store the choice
on their account.**

Storing it on the account rather than the phone matters for three reasons: it
survives a reinstall, it follows them to a second device, and it is the only
way the backend knows which language to write an email or a report in.

The picker belongs on the profile screen, beside sign-out.

---

## 5. What does not need doing

**Money and dates are already right.** Amounts are stored in minor units with
an ISO 4217 currency, which is exactly what a locale-aware formatter needs — so
`Intl` will render them correctly per language with no extra data. Zero-decimal
currencies are already handled. Nothing to change.

---

## 6. Suggested order

1. **Foundation, English only.** Add the translation layer, move the 181
   strings into a dictionary, add the picker, default to device language. The
   app looks identical afterwards. This is the step that stops the debt growing.
2. **Backend: store and use the language.** Field on the user, into the email
   templates, into the prompts.
3. **Chinese.** Font first, then translation, then a read-through by someone
   who speaks it.
4. **Arabic, as its own project.** Layout mirroring, a device pass, and a
   reviewer who reads it.

Doing 1 before the copy settles is still worth it — the strings move, but
moving a dictionary entry is cheaper than finding the string in a screen again.
Doing 3 before 2 is not: a translated app around an English audit is a worse
result than no translation at all.

---

## 7. Questions to settle first

1. **Which languages, actually?** Chinese and Arabic are assumptions from the
   PRD's market list, not a decision anyone has recorded.
2. **Does the audit answer in the founder's language, or always in English?**
   An investor reading a summary may not share the founder's language — so this
   may need to be two languages per report, not one.
3. **Who translates?** Machine translation of an interface is usually passable;
   machine translation of a financial verdict a founder acts on is not.
4. **Does the investor side need it at all?** It may be that founders are local
   and investors are international, in which case the two sides have different
   answers.
