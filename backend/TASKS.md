## Phase 2 — Audit engine

- [x] **T2.1 AI client** — `ai/client.py` with model tiering, structured-output validation, retry-on-invalid, prompt versioning, injection guards. *Done when: a call returns schema-valid JSON or fails cleanly.* — **closed 2026-07-31: the first real Anthropic API calls in this project's history.** `ANTHROPIC_API_KEY` was set and `tests/integration/test_ai_live.py` ran green (3 passed, 108s) on `claude-sonnet-5`. That proves the three things the mocked tests could not: the API **accepts** the request shape (`output_config` carrying a `json_schema` + `effort`, `thinking: {"type": "adaptive"}`, streamed), it accepts a `transform_schema`'d wire schema with nested `$defs`, a `StrEnum`, and a bounded integer — the `minimum`-reaching-the-API 400 this was most at risk of — and the usage figures parse into `AiUsage` carrying real numbers, so per-audit costing has something to read. **Not** that caching was exercised — the live prefix is one sentence, far below the 1024-token minimum on `claude-sonnet-5`, so both cache counters are necessarily zero. The test asserted `cache_read >= 0` and `total_input >= input`, which are arithmetically incapable of failing; it now asserts the counters are exactly zero and the token figures non-zero, which can. Built offline first: `ai/client.py`, `ai/schemas.py`, `ai/guards.py`, `ai/caching.py`, `ai/prompts/`, 47 tests through an injected fake SDK client. **Why `[x]` when T1.2a and T1.5 sit at `[~]`:** this done-when is disjunctive — "returns schema-valid JSON *or* fails cleanly" — and the accept-the-request-shape half was verified live. T1.5's ("one upload, one download") has no verified half at all. The unproven paths below are real and tracked, but they are beyond this task's bar, not short of it.
  - **A config-parsing bug nearly made the first call a confusing 404**, and it is worth remembering because no test could see it: an inline comment after a *blank* `.env` key is read as that key's value, so `AI_MODEL_AUDIT=  # strongest model…` resolved the audit model id to the comment sentence. `conftest` sets `env_file = None`, so the suite was green throughout. `6035538` fixed it with a regression test on `.env.example` — **the wrong depth**, since that lints one file's formatting and leaves the operator's real `.env` (the file that actually decides the model id) unguarded. Now fixed at the parse layer instead: `_blank_to_none` treats a value whose stripped form starts with `#` as unset, since no setting can legitimately begin with one, and the `AI_MODEL_*` fields carry it via `BlankableStr`. The `.env.example` lint stays as a style rule. The suite's own hand-rolled `.env` reader in `conftest` had the same hole and was **worse** — it never stripped inline comments at all, so `ANTHROPIC_API_KEY=sk-…  # prod key` returned a non-`None` key with the comment glued on, meaning `requires_anthropic_key` would *not* skip and the live tests would fail as a 401 that reads like a revoked key. Both are closed with tests.
  - **Only the chat tier has been exercised live.** The live tests are deliberately cheap — small schema, trivial prompt, `claude-sonnet-5`. `claude-opus-5` at high effort, the 16k audit budget, and the retry-on-mismatch and refusal paths are all still unproven against the real API. The refusal path especially: a cyber-category decline on a security startup's documents is a real risk (see the fallbacks note below), and nothing has yet made the model refuse.
  - **Design calls worth knowing.** The live run did not confirm these — it exercised the chat tier only, so read each one as a design rationale, and see the bullet above for which of them remain unproven against the API:
    - **The schema goes over as `output_config`, not the SDK's `output_format`.** With `output_format=Model` the SDK parses inside stream accumulation (at `content_block_stop`), so a truncated body raises `pydantic.ValidationError` *before* `stop_reason` can be read — collapsing three different failures into one indistinguishable error. Passing the wire schema through `output_config` disables SDK-side parsing and leaves `stop_reason` observable.
    - **Three failure modes, three handlers, asserted on call count.** `refusal` raises immediately (an identical retry earns an identical refusal); `max_tokens` raises immediately (a same-budget retry truncates identically and bills twice — thinking is on by default on the audit model and shares the budget); only a schema mismatch on a complete response is retried, once, with the failing field paths fed back in a **user** turn. A last-assistant-turn prefill is a 400 on the audit model.
    - **The schema is still run through the SDK's `transform_schema`.** The API rejects `minimum`/`maximum`/`minLength`, which pydantic emits freely; `transform_schema` demotes them to prose in the field description and forces `additionalProperties: false`. A raw `model_json_schema()` would 400 the first time a rubric declares a bounded score. Those bounds are then enforced by our own validation — which is what makes the mismatch-retry path fire on them.
    - **Model ids live in `ai/client.py`, not as `core/config.py` defaults** — the config comment asks that no model choice be smuggled in as a default, and T2.1 is where the choice belongs. Audits `claude-opus-5` at high effort, chat `claude-sonnet-5` at low. `AI_MODEL_*` still override per environment. `AI_MAX_OUTPUT_TOKENS` is a **ceiling** over both tiers, not a value: one number cannot serve a 16k audit and a 4k chat reply.
    - **Injection defence is structural, not lexical.** Untrusted spans are fenced with a per-call random nonce, so a document cannot close a fence it cannot predict. There is deliberately no blocklist of phrases — scanning for "ignore previous instructions" is unwinnable and worse than useless because it looks like protection. Only control characters are stripped; prose passes through untouched, because mangling a founder's document changes what the audit is auditing.
    - **Citations are required for conclusions, not for `insufficient_data`.** A hard "always cite" would leave the model two ways out when there is genuinely nothing to cite: invent a citation or invent a verdict. Both are the failure `CLAUDE.md` §5 exists to prevent.
    - **Budgets are measured, not enforced** (enforcement is T5.5). A successful call returns an `AiCallRecord` with user attribution, timestamp, and the full token split including the cache figures — costing from `input_tokens` alone under-reports the moment caching works, since it counts only the uncached remainder. **Failures carry their usage on the exception** (`AiError.usage`), because every one of them was billed and the three most expensive calls this client can make are all failures: a truncated audit runs to the full 16k cap at high effort, and a mismatch retry bills twice. A budget fed only by successful records would under-count precisely the spend it exists to cap; `complete` folds earlier attempts into the exception so a refusal on the retry reports both.
    - **The prompt registry is process-global and never resets** — that is what makes "a published version cannot be republished" enforceable, but it means a T2.6 fixture registering a prompt *per test* will hit `already published` on the second test in the same process. Register at module import, or give each test a distinct version number.
    - **Refusal fallbacks are still not wired up, but the reason has changed.** A cyber-category refusal is a real risk here — auditing a security startup means feeding a security product's description to a classifier trained to decline that material — and the server-side `fallbacks` parameter is the fix. The original excuse (wire shape unverifiable without a live call) **expired when the key arrived**: it is `fallbacks="default"` with the `server-side-fallback-2026-07-01` beta, and cyber-category refusals route to `claude-opus-4-8`. What blocks it now is scope, not knowledge — it needs the beta messages namespace plus a beta header on the one chokepoint every model call passes through. Tracked as its own open follow-up below; **documented, not implemented.**

- [~] **T2.4 Extraction stage** — documents → Startup Profile fields with source/confidence and missing-field flags. *Done when: a sample deck+financials populate the profile.* — **half done, same shape as T1.2a and T1.5**: `audit/extraction.py` is built and tested (28 tests, real xlsx/pptx/docx bytes, no network, no DB), but **no document has ever been read end-to-end** because R2 is unset and nothing has been uploaded. The function takes **bytes, not a storage key**, which is what let it be built and proven offline; wiring it to storage is a thin adapter in `pipeline.py` (T2.8). One real deck + financials through a real bucket closes this. Design calls:
  - **PDFs and images go to the API as native `document`/`image` blocks, not through a text extractor** — so **no PDF dependency was added at all**. A deck is a design artefact: an extractor returns the speaker notes and misses the chart carrying the number, and a photographed cap table has no text layer. The three parsers added (`openpyxl`, `python-pptx`, `python-docx`, approved 2026-08-01) cover only the Office formats the API cannot ingest directly.

Inlining a PDF's text unfenced would reopen exactly the hole `ai/guards.py` exists to close. A test proves a CSV cell containing a closing tag cannot terminate the fence early.

- [~] **T2.4a Wire extraction into the pipeline** — fetch document bytes from R2, run `extract_fields`, merge with `merge_into_profile`, persist, recompute `missing_fields`. — **built and unit-tested (21 tests, no DB, no network); no document has yet gone through end to end.** Until this change `run_pipeline` was called with `documents=()` on every path, so a founder could upload a deck and their financials and the audit would silently score the typed profile alone — the product's central claim not being delivered. Built: `core/storage.get_object` (the byte fetch that did not exist), `intake.load_auditable_documents` / `auditable_storage_keys`, `extraction.fenced_documents`, and the composition in `workers/tasks._score`. Closes when one real deck + financials run through a deployed worker. Design calls:
  - **The extracted fields are merged in memory and deliberately never written back to `StartupProfile.fields`.** The task line says "persist" and this change does not, because persisting would move the idempotency fingerprint — `input_fingerprint` hashes that JSONB, so the next *identical* submission would miss the unique key, mint a fresh AuditRun and bill a second `claude-opus-5` high-effort pass over evidence already scored. It is also not self-correcting: extraction runs again, merges again, the hash moves again, and `merge_into_profile` dropping a low-confidence value on one run but keeping it on the next makes it non-convergent. The founder's profile stays exactly what they typed; the audit sees the enriched view. **Persisting it is still worth doing** and needs the fingerprint taken *before* extraction, or extraction excluded from the hash input — a deliberate change, not a line to add in a hurry. The guard is structural rather than behavioural: `_score` accepts no session, so persistence is not reachable from it, and `test_the_scoring_stage_is_given_no_way_to_write_to_the_database` fails if anyone threads one in.
  - **`document_keys` is populated now, and that half is not optional.** A founder who uploads the financials the first run said were missing must not be handed the pre-upload verdict — a regression that looks exactly like the idempotency cache working correctly. `auditable_storage_keys` is a separate query from the document fetch on purpose: the fingerprint is computed on the request thread, where pulling megabytes out of R2 would be the wrong thing entirely.
  - **Scoring sees strictly less than extraction does, and this is the real finding of the task.** `extract_fields` sends a PDF or a photograph to the API as a native `document`/`image` block, which is how a scanned deck gets read at all. But `consistency.find_contradictions` and `rubric.v1.score` both inline `UntrustedContent.text`, so neither can receive a native block — and there is deliberately no PDF text extractor in this project (T2.4: a deck is a design artefact; an extractor returns the speaker notes and misses the chart carrying the number). So a PDF's content reaches scoring **through the fields extraction read out of it**, rendered by `render_profile_facts` with `[source: document]` and a citation — which is coherent — but it never reaches the *semantic contradiction pass*, which compares raw sources against each other. **A deck that contradicts a spreadsheet is therefore caught only where the disagreement shows up in an extracted field.** Closing that means teaching those two callers to carry native blocks; converting the PDF to text here would be the lossy version of the same thing and was refused.
  - **An extraction failure costs evidence, not the audit.** A refusal or a timeout in stage 1 is logged and the run continues on the profile as submitted, with the documents still reaching the later stages as fenced text. Telling a founder their audit failed when most of it could have run is the worse answer.
  - **A document whose object is missing or oversized is skipped and named, not fatal.** `get_object` returns `None` for a missing key rather than raising (a deleted object is a state the worker has to survive) and refuses anything over 25 MiB using the reported `Content-Length`, before the body is read — a worker OOM-killed mid-audit strands the run in `running`, which is the failure with no owner.
  - **`_is_auditable` allows `SKIPPED`, and that is the one line to change when the scanner lands.** No scanner is wired yet (T5.5), so `scan_document` settles every upload at `SKIPPED`; refusing it would mean refusing every document that exists. `INFECTED` is refused today.
- [x] **T2.5 Consistency check** — cross-document contradiction detection → `dataIntegrityScore` + contradiction list. *Done when: a planted contradiction is flagged.* — **must also carry unit-scale plausibility**, which T2.2a proved cannot live at the field boundary: `monthly_churn_percent: 0.02` meaning 2% is indistinguishable from a genuine 0.02% by range alone, and it yields an LTV **100x too high**. Only a cross-field check — churn against customer count and revenue, revenue against run rate — can see it. Same class of error as major units submitted where minor units belong. — **`audit/consistency.py`, 21 tests, done.** The planted-contradiction done-when is met by the scale half, which needs no model and no network; the semantic half is built and unit-tested through the fake client. Design calls:
  - **Two mechanisms, deliberately not merged.** Scale plausibility is arithmetic and lives in **code** — D9 says money is math, and a model judging it would also break T2.9's same-input-same-score requirement, since the answer would move between runs. Contradiction detection is semantic (a deck claiming 34 customers against financials showing 12) and is the model's half; it must cite **both** sides.
  - **Thresholds are deliberately loose — 10x, never 2x.** Telling a founder their revenue looks wrong when it is right costs more trust than missing one subtle error, and this score feeds a verdict about their company. Every check has a paired false-positive test; a 3x discrepancy is explicitly *not* reported, because a business that grew or shrank is normal.
  - **Churn is checked against customer count, not range.** This is the T2.2a lesson made concrete: `0.02` is indistinguishable from a genuine `0.02%` by range alone, so the test is "does this rate describe **less than one customer** per month?" At 50,000 customers, 0.02% is ten people — real and measured. At 34 customers it is 0.0068 people, which nobody measured. A range check alone would have told a large healthy business its best metric looks like a mistake.
  - **`CERTAIN` vs `LIKELY`.** Head-count impossibilities (more founders than staff) cannot be false positives and weigh more in the score than threshold-crossings that could be.
  - **Two audiences, two messages, and a third that gets neither.** Every finding carries a founder-facing `message` (plain, actionable, and **never accusatory** — a mistyped unit is far likelier than dishonesty, and a tool that implies otherwise will not be used twice) and an engineer-facing `detail` naming the comparison that fired. `log_context()` returns **only the code, severity, and field names** — no figures, per `CLAUDE.md` §4. Showing a founder their own numbers is not a leak; writing them to a log every operator can read is. Tests enforce all three.
  - **`data_integrity_score` is arithmetic over a fixed table**, floored at 0, and a test asserts ten runs of the same input give one score — T2.9's requirement proven here rather than deferred to the harness.

  - **7 core dimensions + 1 fundability-only + 3 saleability-only.** The overlap is real — both verdicts care about margins and about whether the data is trustworthy — so the core is shared and only the genuinely divergent questions are scoped. - [x] **T2.7 Scoring + synthesis** — dimensional scoring → verdicts (fundable/saleable) + founder report + action plan; provisional on thin data. *Done when: a full report is produced and grounded in stages 2.4–2.6.* — **`audit/synthesis.py`, 17 tests, done.** Consumes `rubric.v1.score` output plus `consistency`'s findings and integrity score; produces both verdicts, the report, and the action plan. Design calls:
  - **The verdict is computed, not asked for.** Every input already came from a model, but turning scores into "fundable" is arithmetic over a documented rule. Three reasons it cannot be a second opinion: T2.9 needs the same input to give the same verdict and a model may not agree with itself twice; a founder told "not yet" is owed a reason, and a rule can be shown to them where a judgement cannot; and `CLAUDE.md` §5's ban on a false "fundable" is a **guarantee**, which has to be enforced by something that cannot be talked out of it.

  - **One provisional dimension makes the whole verdict provisional.** Confidence does not average out.
  - **The action plan sorts unassessable dimensions first**, then worst-scoring. "We could not assess this" is cheaper to fix than a low score *and* it is what blocks the verdict.

    - **`202` for new work, `200` for a run that already covers these inputs.** The idempotency guarantee surfaced in the status code rather than hidden behind a silent no-op, so a client can tell "queued" from "you already have this".
    - **`AuditRunResponse` has no `report` field in any state**, and a test asserts its absence on the schema rather than on one response — adding one later fails loudly instead of routing the internal report around the tier rules for every founder at once (§4).

Failures are recorded on the row and **not** re-raised, because an RQ auto-retry is another billed pass over the same evidence.

    - **`run_pipeline` takes no session and no ORM object**, only a `ProfileSnapshot` of plain data. Not style: CI has no `DATABASE_URL`, so a session-bound pipeline would be a pipeline no push ever runs. The one part that genuinely needs the database — benchmark lookup — is split into `assemble_benchmark_context`, which hands the pipeline a string. Same seam `extract_fields` (bytes, not a storage key) and `v1.score` (rendered text, not `Benchmark` rows) already use.

    - **A dimension the model did not return is padded as `insufficient_data`** before synthesis. T2.7's tests cannot see it because their fixtures always build the complete set; the pipeline is the first caller where completeness is a model's promise.     - **Rendering order is fixed, never reflection or insertion order** — the rendered prompt is part of "same input" for T2.9, so profile fields follow `PROFILE_FIELDS` declaration order and benchmarks follow `BenchmarkMetric`'s, whatever order the JSONB or the lookup produced.

    - Still absent by design: stage 1 (extraction) is T2.4a, and stage 6 (persistence) belongs to the service that owns the AuditRun row.
  - **Embeddings are deliberately absent from `0010`.** The task lists them, but **Anthropic has no embeddings endpoint**, and a vector's dimension is provider-specific (1024 Voyage, 1536 OpenAI). Declaring a column would silently commit to a provider nobody chose; `pgvector>=0.3` is already a dependency and used **nowhere**. Adding it is one migration once that call is made — see the open follow-up.
  - **The unique key is the guarantee, not an optimisation.** An audit is the most expensive call the platform makes (D16), so a duplicate is a real charge for a verdict the founder already has. `(startup_id, input_hash, rubric_version)` closes the race an RQ `job_id` cannot: a job id lapses the moment the job finishes, after which only the database still refuses. A test proves the `IntegrityError`, and it was proven able to fail.
  - **`document_keys` is in the fingerprint now though it is always empty.** Once T2.4a wires storage, a founder who uploads the missing financials and re-runs must not receive the pre-upload verdict — a regression that would look exactly like the cache working.

  - **Provenance is a field, not a footnote.** Every expectation carries `reviewed_by`: `deterministic` (2 companies — the verdict comes from the integrity floor or the coverage ratio and no model output reaches it, so there is no circularity to worry about) or `assistant-draft` (6 — scored by Claude against the published rubric, on the owner's explicit instruction after they said they did not know how to score them). **The audit engine runs on the same model family that wrote those six**, so an agreement figure over them is partly a model agreeing with itself. `qualified_ids()` groups by provenance so the eval report cannot print one blended percentage and call it accuracy, and `test_accuracy_is_not_claimed_by_this_file` asserts the caveat is still required.

The four fixtures that assert a non-provisional level were enriched to reach it; the rest were corrected to `provisional`. `test_the_expected_level_is_one_the_profile_can_reach` makes it permanent, and was proven able to fail against the pre-fix expectations.
  - **Integrity expectations are exact, not banded.** `data_integrity_score` is arithmetic over a fixed penalty table, so a band is slack hiding a wrong answer — the first draft banded `unit-error-kobo` at 0–49, which passes for values only two of its three findings could produce. All eight are now single values (100, 100, 100, 45, 100, 100, 100, 75) and each was computed from the real `check_scale`/`check_team` before being written down.
  - **`covered < 0.5` is a strict comparison, so exactly half is a coin flip.** `pre-revenue-deeptech` sat on 4/8 and would have swung between `provisional` and `insufficient_data` on any single field change. `test_no_fixture_sits_on_the_coverage_boundary` refuses that, whether or not the fixture is currently green.
  - **The narrative-length proxy is crude and says so.** `market_opportunity` and `scalability` have no structured field, so the only mechanical question left is whether anything was written at all — 240 characters. It is defensible only because every fixture is far from the line (enriched: 322–593; unenriched: 0–52), and `test_narrative_evidence_is_not_a_borderline_call` asserts that margin rather than the threshold. Same shape as rubric v1's "every criterion is over 30 characters", and honest about being the same shape.
  - **A band cannot carry an ordering claim, so one fixture carries a flag instead.** `founder-dependent-agency` exists to prove the two verdicts can diverge, and two bands — however tight — are both satisfied by a run that scored fundability and saleability identically, which is the exact failure it is meant to catch. Its bands are therefore made non-overlapping (46–69 against 32–45) and it sets `saleability_below_fundability`, which tells Layer B to compare the two *observed* scores directly. `test_a_divergence_claim_is_carried_by_more_than_two_overlapping_bands` keeps the bands from quietly contradicting the flag.
  - **The band has to be able to produce the level, not just the score type.** Once coverage is complete, `ready` and `not_yet` are separated by `READY_THRESHOLD` alone — so a `not_yet` band reaching 70 describes a run that would have been `ready`. `founder-dependent-agency` had exactly that (46–70) and it would have failed on a **billed** run, reading as "the model disagreed" rather than "this was never satisfiable". Caught by extending `test_the_expected_level_is_one_the_profile_can_reach`, which is the same class of bug the None-vs-band check already covers on the other axis.
  - **Layer B (`test_golden_accuracy.py` + the eval report) is deliberately not built yet.** It is billed — `claude-opus-5` at high effort, 8 companies, two calls each — and `CLAUDE.md` §2.5 makes spending the owner's call. It also should not be written until the field-set question below is answered, because the first run's most likely outcome is "everything came back `provisional`", which would be a finding about the intake form rather than about the model.

## Phase 3 — Readiness loop

- [x] **T3.1 Task generation** — required/recommended tasks from audit gaps, specific to the report; link to products where relevant. *Done when: gaps produce correct required vs recommended tasks.* — **done 2026-08-05.** `readiness/generation.py` (pure), `models.ReadinessTask`, migration `0012_readiness_tasks`, three endpoints, and the call from `workers.tasks.run_audit_async`. 23 unit tests, 20 database-backed, 2 worker-wiring, and a 19-check pass over a live server. Until this landed **the action plan reached nothing a founder could act on** — 44 items were computed, serialised into `AuditRun.report`, and that was the end of them; the product's whole readiness loop started at a JSONB column nobody could work through. Design calls:
  - **`required` is computed from `READY_THRESHOLD`, not judged.** PRD §4.2 says blocking gaps become required tasks, so "blocking" has to mean something arithmetic, and it means exactly what `synthesis._verdict_for` means: a dimension that could not be scored (trips the `thin` rule, which forces `provisional` however strong everything else is) or scored below the threshold. Asking a model instead would make a founder's *obligations* non-deterministic — the same report generating a required task one day and a recommended one the next, which is T2.9's guarantee moved downstream. The constant is imported rather than restated, so it cannot drift. The boundary is tested directly: `>= READY_THRESHOLD` is not blocking, matching the verdict rule, and an off-by-one there is invisible in every other test.
  - **A re-audit reconciles; it never rewrites.** Every audit produces a *complete* action plan, so the obvious implementation — delete this startup's tasks, insert the new plan — throws away the founder's progress on every task each time they re-audit, and the suite stays green because each individual row looks correct. `uq_readiness_tasks_action` on (startup, action fingerprint) makes the second audit *find* the existing row. Same reasoning as `uq_audit_runs_idempotency`, one layer up: the fingerprint is over the gap rather than over the inputs.
  - **Only an untouched task can be retired.** A gap the new audit stops raising goes `obsolete` — but solely from `open`. Anything carrying evidence keeps its state and its history, because a later audit dropping a gap does not make the work untrue. `failed` is the case that looks retirable and is not: it has evidence attached and a founder owed the reason. A retired gap that comes back **reopens**, so a regression is visible rather than silently absent.
  - **The fingerprint normalises whitespace and case, and nothing else.** Rewording defeats it and a rephrased action produces a second task beside the first. Asserted in a test rather than left as a surprise. The honest fix is semantic matching, which needs embeddings — still blocked on the provider decision below. Visible duplicates are the safer failure than silently merging two genuinely different instructions.
  - **No endpoint completes a task.** D10 makes readiness earned by doing the work, uploading evidence, and having it assessed — so there is no request schema that carries a status, and the *absence* of one is what enforces it. A founder-settable status would clear the T3.6 visibility gate by tapping a button eleven times.
  - **The report commits first; generation is best-effort in its own transaction.** The first draft did both in one transaction, reasoning that a stored report whose plan reached no task is a founder told "not yet" with nothing to do about it. **That was wrong, and the reason is structural**: everything after the `_score` call sits *outside* the `try` that covers scoring, so a raise from generation propagated straight out of `run_audit_async` onto RQ's failed queue for an automatic retry — and every retry re-enters at the top for another billed `claude-opus-5` high-effort pass. Sharing the transaction made it strictly worse: the rollback took `mark_succeeded` with it, discarding a report already paid for and stranding the run in `running` for the lease to recover half an hour later — the exact three-bug cluster `8743273` closed, reintroduced through a new door. Verified by raising from `generate_for_report` and watching the exception escape the handler. `_generate_readiness_tasks` is now modelled on `_record_failure`: own session, swallows, logs at exception level so Sentry raises it.
    - **What a failure now costs, stated rather than hidden:** the founder has their report and an empty task list, and nothing retries. The next *succeeding* audit for that startup regenerates the whole plan — but `request_audit` is idempotent on the profile fingerprint, so an unchanged profile mints no new run. Recovery needs the founder to change something or an operator to notice. That residue is the price of never re-billing an audit, and it is the right way round.
    - `run_audit_async` remains the composition root — `audit` never learns what a `ReadinessTask` is, and `readiness` reads the typed report rather than re-parsing the JSONB just written from it. Proven both ways by mutation: removing the call turns the wiring test red, and moving generation back inside the report's transaction turns the no-propagation test red.
  - **Generation is read-then-insert, so a concurrent duplicate is possible and is now cheap.** `find_by_fingerprints` then `add` has the same gap `claim()` had: `uq_readiness_tasks_action` stops the second *row*, nothing stops the second *writer*. Two runs for one startup finishing concurrently both read no tasks and both insert the same fingerprints; the loser gets an `IntegrityError`. **Not reachable on today's single-worker deploy** — `render.yaml` declares one worker and RQ processes one job at a time — and worth re-checking before scaling the worker past one instance. With generation isolated it costs the losing run's tasks and a log line, not the report; the winner's tasks already cover the same gaps. A savepoint per insert would close it properly and is not built, because the machinery is not yet earned.
  - **The full `TaskStatus` vocabulary is declared although only two states are reachable.** `submitted`/`passed`/`failed`/`needs_more` are T3.5's to write. The column is a check-constrained enum, so adding values later is a migration on live rows *plus* a client release; declaring now costs a docstring. `CLIENTS.md` says which are reachable so nobody builds against a promise that has not landed.
  - **`audit_run_id` is the run that most *recently* raised the gap**, refreshed on regeneration, nullable with `ON DELETE SET NULL`. A task is a live instruction and "why am I being asked this" must reach the report currently asking; `created_at` records when it first appeared. Deleting a run must not delete a founder's task history.
  - **No `product_id` column yet.** T3.1 asks for tasks to link to products "where relevant" and T3.2 creates the catalogue; a foreign key cannot point at a table that does not exist, and a loose text column would be a second format to migrate away from. One additive nullable column with T3.2.
  - **`GET .../tasks/summary` is declared before `GET .../tasks/{task_id}`** — reversed, `summary` parses as a task id and 422s. Route ordering is not visible to any unit test, which is why it was checked over HTTP against a running server.

- [x] **T3.5 Evidence upload + assessment** — upload evidence; `assess_evidence` job grades against per-task criteria → pass/fail/needs-more. *Done when: weak evidence fails with reasons; strong evidence passes.* — **done 2026-08-05.** `readiness/assessment.py` (prompt + grading call), `readiness/evidence.py` (lifecycle + the attempt cap), the `Evidence` model, migration `0013`, five endpoints, and `workers.tasks.assess_evidence`. 15 unit tests, 19 database-backed security tests, 6 worker tests. This is what makes a task completable: before it, `TaskStatus.PASSED` was declared and unreachable, so the readiness loop had a first half and no second. Design calls:
  - **The criterion is the task's own `action`, unmodified.** T2.6 writes every `unmet_criteria` entry as a completable action *specifically so* something downstream can grade against it, so the string handed to the grader is the same string the founder was shown. A founder therefore can never fail against a hidden standard, and there is no paraphrase step to drift.
  - **Ambiguity resolves to `needs_more`, never to a pass or a fail.** `CLAUDE.md` §5's thin-data guarantee one layer below the audit: the verdict machinery refuses to call thin evidence `ready`, and evidence that gestures at the work without showing it gets the same treatment. Both error directions are expensive here — a false pass admits an unready startup to investors, a false fail burns one of three attempts — so the prompt names the rule twice and a unit test asserts it is still in the text.
  - **Three graded attempts per task, then the task locks.** Owner's call, asked rather than guessed (it was an open question in this file). A cap has to exist and that part is not a preference: grading is a model call, a model does not answer identically twice, so unlimited attempts means a determined founder eventually passes anything — and each attempt is a billed `AUDIT`-tier call with no per-user budget behind it yet (T5.5). **Three is untuned**, the same false-precision problem as `READY_THRESHOLD`.
  - **Locking is not failing.** At the cap `status` stays whatever the last grading said and the *upload* is refused. A `fail` is a statement about the work; a lock is a statement about the process, and conflating them tells a founder their business fell short when they actually ran out of tries.
  - **The counter increments on the grading, not the upload.** Three files attached to one task is one attempt, because the grader reads a task's outstanding submissions as one set — a founder proving "publish a pricing page" may reasonably attach the screenshot *and* the invoice that dates it, and grading those separately would fail both for being incomplete alone and bill twice for it. Counting uploads would let one careful submission exhaust the whole budget.
  - **The cap is enforced at completion and again in the worker, not only at reservation.** Checking it once, where the upload is requested, left it trivially bypassable: reservations are cheap and unmetered, so a founder could take ten tickets while the counter read zero and cash them one at a time afterwards, each completion dispatching a grading that walked the counter past its ceiling unchecked — the guard on the gate defeated entirely. **The state that matters is the state at the moment work is dispatched.** `complete_evidence_upload` therefore re-checks (and refuses before the storage call, so a founder past the cap costs nothing), and `assess_evidence_async` checks once more immediately before spending, because a cap enforced only at the HTTP boundary is one a queue reordering can step around. Found by re-reading the flow rather than by a test, and proven by mutation: removing the completion check turns `test_tickets_reserved_before_the_cap_cannot_be_cashed_after_it` red.
  - **A rejected upload and a failed grading both cost nothing.** Storage validation happens before the model, and a provider outage is not a founder's mistake — `record_assessment_failure` returns the task to `open` and leaves the counter alone, or a worker restart would silently spend a founder's tries.
  - **Reopening is admin-only and audit-logged.** It is the single lever that undoes the guard on the investor-visibility gate, so `AuditAction.TASK_REOPENED` records who pulled it. A founder resetting their own counter is not a cap. A `passed` task is reopenable too, deliberately: that is the dispute path, and refusing it would make a database edit the only way to correct a false pass.
  - **`AssessmentOutcome` and `TaskStatus` are separate vocabularies joined by an explicit mapping.** Sharing values would make the model's output *be* the task state, which is exactly the "uploads must not act as instructions" line in §5. The mapping's range is asserted, not just its keys: no outcome can write `obsolete` or `open`, so a grader cannot make a required task vanish.
  - **Idempotence comes from the query, not a lease.** `list_gradable` returns only `ready` rows with no `outcome`, so a redelivered job finds nothing and spends nothing. The audit needed a conditional UPDATE because its row is claimable in several states; here "already graded" is written on the rows themselves and there is nothing to race over.
  - **Nothing readable costs nothing.** An empty or unfetchable submission returns `needs_more` with a reason and `attempts=0` on the record, without a model call — the same zero-cost shape `extract_fields` uses. Paying an `AUDIT`-tier call to be told a zero-byte file is unreadable is money for an answer already known.
  - **`document_blocks` and `safe_filename` were promoted from private**, not copied. Evidence is the same problem as a deck — a PDF or photograph must go as a native API block and a founder's filename must be reduced the same way — and a second copy is a second place to forget a rule.
- [x] **T3.6 Re-audit + gating** — passing evidence re-audits affected dimensions; investor-visibility gate = audit cleared AND required tasks passed; dispute/re-audit path. *Done when: a startup only becomes investor-visible after the gate is satisfied; `tests/security` prove it.* — **done 2026-08-05.** The gate is three conditions in `investor.DiscoveryRepository._visible`; the re-audit is passed evidence joining the audit's inputs; the dispute path already existed. 18 database-backed security tests, proven able to fail by removing the gate (8 red). Design calls:
  - **The gate is enforced at the read, not at `publish`.** Consent and eligibility go stale on different schedules: a founder who was eligible when they published stops being eligible the moment a re-audit raises a new required gap, and a check written at publish time would leave them discoverable anyway. Deciding it in the discovery query means the answer cannot be out of date. `intake.set_discoverability` stays exactly what it already documented itself to be — consent, unconditional to give and to withdraw — and its docstring's prediction that T3.6 would "constrain the publish branch only" turned out to be the wrong call; the read is the wall.
  - **In SQL, in `_base`, for the reason that module already gives.** A filter applied after the fact is one forgotten call away from publishing every founder on the platform. There is no unfiltered variant of this query to reach for by mistake, and the gate is now inside that same guarantee.
  - **Outstanding is scoped to the tasks the *latest* run raised** (`audit_run_id == latest.id`), not every task ever. This is the call that matters and a naive predicate gets it wrong: `_retire_unraised` retires only `OPEN` rows — deliberately, so a founder's evidence is never erased — so a task graded `failed` keeps that status forever, even after a later audit stops raising the gap. Counting it would leave that founder **permanently invisible with no self-service path**: the gap is absent from the current report so no new evidence can address it, and an admin reopen sets it to `open`, which is still not `passed`. Scoping to the latest run makes the gate mean "outstanding according to the report an investor would actually be shown", which is what PRD §4.2 says.
  - **`obsolete` is excluded as well as `passed`** — belt-and-braces, since `_refresh` reopens a raised task out of `obsolete` so the two cannot co-occur. If that invariant ever breaks, not blocking a founder over a retired task is the safe direction.
  - **A tiebreaker on `id`, in both queries, and it is not decoration.** Postgres `now()` is the *transaction* timestamp, so two runs written in one transaction share `created_at` to the microsecond; with no tiebreaker `DISTINCT ON` picks between them arbitrarily and not necessarily the same way twice. `_visible` and `AuditRunRepository.latest_succeeded` must resolve to the **same** run or the founder's summary disagrees with what an investor can see — a founder told they have cleared while discovery hides them. Found by three failing tests, not by reading.
  - **Passed evidence joins the audit's inputs, and that is the whole re-audit.** `input_fingerprint` hashes the document keys, so a founder who worked through their plan and had the proof graded has changed what the audit reasons over — the hash moves and `POST /v1/startups/{id}/audits` mints a genuinely new run instead of handing back the pre-work verdict, which is a regression that would look exactly like the idempotency cache working correctly. Keys are sorted so the order two queries return rows in cannot mint a second run for identical inputs.
  - **Evidence is selected by joining to the task, not by `Evidence.outcome`.** A task reopened and graded again must not keep feeding the audit evidence from the grading that was overturned; the task's *current* status is the question, so the task is what is asked.
  - **No automatic re-audit on a pass.** It would put a billed job dispatch inside the grading transaction — the thing this codebase has already been bitten by twice — and the trigger condition (`required_open` hitting zero) is computed from rows the same transaction just wrote, so a redelivery or a concurrent grading could satisfy it twice. The founder-requested path already exists, is idempotent, and now returns a real new run. The summary tells them it is worth pressing.
  - **No second dispute path.** The task line mentions one; `POST /v1/admin/tasks/{task_id}/reopen` from T3.5 already *is* it — admin-only, audit-logged, and deliberately able to reopen a `passed` task so a false pass can be corrected in either direction. Building a second would be two doors to the same room.
  - **`ReadinessSummary` reports eligibility and consent separately** (`gate_cleared` vs `investor_visible`). They fail for different reasons and are fixed by different actions, so collapsing them would leave a founder unable to tell "you have work left" from "you have not opted in". Its counts are scoped the same way the gate is, so `required_open == 0` means exactly what the gate tests rather than something adjacent to it.

  - **Three models, not one model with `exclude=`.** A serializer that cannot *declare* a field cannot leak it.   - **The leak tests use sentinels, not key lists.** Every founder-only string in the fixture is a unique marker and the investor assertions search the **entire serialized document** for each one. Proven able to fail: injecting a `rationale` into the investor verdict turned the suite red.

Section 4 draws the tier at what each audience is *served*.
  - **Admin is a separate route, not the founder route widened by role.** Two audiences, two routes, so a change to one cannot silently widen the other. The role check therefore lives in the router and is asserted directly, since the service method deliberately does not know which door it was called through.
  - **No report is `404`, never a `200` carrying nulls.** A blank verdict rendered as a real one is the same false-verdict failure `CLAUDE.md` §5 forbids, arriving through the transport instead of through the model.

  - **Migrations run as `preDeployCommand` on the web service only** — running it on both would have two processes applying the same migrations concurrently. Not available on Render's free tier; noted in `DEPLOY.md`.
  - **Still open, and both are in `DEPLOY.md` rather than buried here:** CI does not gate deploys (Render deploys on push regardless of the workflow), and there is still no per-user AI budget cap (T5.5) behind a publicly reachable audit endpoint.

- [x] **The three audit-run stranding and double-billing bugs — closed 2026-08-04 by one lease.** They were always one piece of work: a row saying a job is in flight behind a job that no longer exists. `runs.LEASE_SECONDS` (1800) plus `repository.claim`, a single conditional UPDATE, replaces the worker's read-check-write. 9 pure-logic tests in `tests/unit/test_audit_lease.py` (so CI runs them) and 6 against real Postgres in `test_audit_retry.py`. What each one was:
  - **A redelivered job double-billed.** `run_audit_async` loaded the row, checked `status is SUCCEEDED`, then called `mark_running` — three statements with two gaps, and two concurrent deliveries both got through to run the pipeline: two `claude-opus-5` high-effort passes for one verdict, the second `mark_succeeded` overwriting the first report, which is the "different verdict for identical inputs" T2.9 forbids. RQ does **not** dedupe by `job_id`, so nothing upstream closed it either. Now one UPDATE that Postgres serialises on the row; the loser sees `rowcount == 0` and stops.
  - **A run stranded in `running` polled forever.** RQ kills the job at `AUDIT_JOB_TIMEOUT` and releases the `job_id` without writing to the row, so a killed worker or a redeploy mid-call left `RUNNING` with `completed_at` NULL permanently, every resubmission returned it with `200`, and `CLIENTS.md` §5a tells the client to keep polling. A `RUNNING` claim older than the lease is now claimable, and `_is_stranded` re-dispatches it on resubmission.
  - **A run stranded in `queued` with `attempts > 0`** — the same shape from the other direction, when the reset committed and the dispatch was lost. Same branch, keyed on `started_at` being non-NULL.
  - **The lease is deliberately twice the RQ job timeout, and that margin is the safety property.** A shorter lease would be worse than none: it would let a second worker take a claim from a first that is merely slow, which is the double bill it exists to prevent. `test_the_lease_outlasts_the_job_timeout` asserts the relationship rather than the number, so changing either constant alone fails. The cost is a founder waiting up to half an hour for a stranded run to become retryable — cheaper than a double charge.
  - **`FAILED` is deliberately not stranded however old it is.** It has its own capped retry path, and letting the lease reach it would bypass `MAX_AUDIT_ATTEMPTS` — an old failed run would re-dispatch unbounded, the double-spend D14 exists to prevent.
